# Local SQL Server

SQL Server 2022 Developer runs in Docker; the .NET application runs locally.
Developer edition is for development and testing, not production.
Starting this service accepts the [SQL Server license terms](https://go.microsoft.com/fwlink/?LinkId=746388)
through `ACCEPT_EULA=Y`.

## Prerequisites And Setup Order

- Install the .NET 10 SDK; check it with `dotnet --version`.
- Install Docker Desktop with Docker Compose and start its engine; check it
  with `docker info` and `docker compose version`.
- The pinned SQL Server Linux image targets x86-64. These instructions assume
  an Intel Mac; Apple Silicon emulation is not a supported SQL Server host.
- For HTTPS, trust the .NET development certificate with
  `dotnet dev-certs https --trust` and approve the operating-system prompt.

Run all commands from the repository root. The first-run order is:

1. Restore solution packages and local tools:

	```zsh
	dotnet restore ICFAccounting.slnx
	dotnet tool restore
	```

2. Start SQL Server using the hidden password prompt below.
3. Supply `ConnectionStrings__ICFAccounting` and run the explicit database
	update under **Migrations**. This creates `ICFAccounting` and its tables.
4. Configure the API with the same connection string and start it under
	**Run The API**. Creating a database does not start the API.
5. Run the tests under **Test Requirements**. Integration tests provision their
	own SQL Server container; they do not depend on the Compose service.

## Start

Install and start Docker Desktop on your Intel Mac. From the repository root,
enter a strong local password without placing it in shell history:

```zsh
read -rs 'MSSQL_SA_PASSWORD?SQL Server development password: '
export MSSQL_SA_PASSWORD
docker compose -f compose.json up -d --wait sqlserver
```

Pass `-f compose.json` to each Compose command because JSON filenames are not
discovered automatically.

Use at least eight characters with characters from at least three categories:
uppercase letters, lowercase letters, digits, and symbols. Do not commit the
password. Compose rejects a missing or empty password before starting.

The service is available at `localhost,1433` with SQL authentication and login
`sa`. Trust its self-signed certificate only for local development. Set
`MSSQL_PORT` before starting to use a different local port. The port is bound
only to `127.0.0.1`.

The container provisions the SQL Server instance only. Create the
`ICFAccounting` database and its schema explicitly using the migrations below.
The API uses the SQL repository implementations in Data. Supply its connection
string and apply migrations before making accounting requests; no in-memory
fallback is configured.

## Check And Stop

```zsh
docker compose -f compose.json ps
docker compose -f compose.json logs sqlserver
docker compose -f compose.json stop sqlserver
```

Keep `MSSQL_SA_PASSWORD` available in the shell for subsequent Compose commands.
The health check authenticates to SQL Server and runs `SELECT 1`.

Data is stored in the `sqlserver-data` named volume and survives container
recreation and `docker compose -f compose.json down`. Do not use
`docker compose -f compose.json down --volumes`
unless you intend to permanently delete the local SQL Server data.
Changing the environment password does not reset the password in an existing
data volume; use the original password or change it in SQL Server explicitly.

Stopping the API with Ctrl+C does not stop SQL Server. Use `stop sqlserver` to
pause the database service, or `docker compose -f compose.json down` to remove
the service container and network while retaining its data volume. Previously
process-local in-memory data cannot be recovered or migrated; SQL storage
starts empty unless existing records are already present in its volume.

## EF Core Model

The Data project contains `ICFAccountingDbContext` and mappings for pledgers,
pledge categories, pledges, and payments. Domain entities remain independent of
EF Core, with their private constructors, strongly typed IDs, and business rules
unchanged. API startup passes its configuration to Data-owned registration,
which creates one scoped context shared by the scoped SQL repositories.

- IDs use `uniqueidentifier` and are generated by the domain, not the database.
- Required foreign keys prevent deletion of pledgers or categories with pledges,
	and pledges with payments. Relationships do not cascade deletes.
- Amounts use `decimal(38,2)`. An amount-specific type mapping preserves the full
	existing .NET decimal range, including `decimal.MaxValue`, without rounding
	unrepresentable database values into different amounts.
- Audit timestamps use `datetime2(7)` and restore UTC `DateTime.Kind` on reads.
	Payment dates preserve their wall-clock values, without conversion to UTC.
- Names and optional comments use `nvarchar(max)` to retain existing length and
	Unicode support. SQL uses case-insensitive, accent-sensitive collation
	`Latin1_General_100_CI_AS_SC` and native SQL Server GUID ordering.
- Inactive entities remain queryable; no global query filters are applied.

## SQL Repositories

Data contains `SqlServerPledgerRepository`, `SqlServerPledgeCategoryRepository`,
`SqlServerPledgeRepository`, and `SqlServerPledgePaymentRepository`. They implement
the existing domain repository interfaces using `ICFAccountingDbContext`.
API startup registers the context and all four repositories as scoped services.
Application services remain scoped, and `TimeProvider` remains a singleton.
Missing or blank `ConnectionStrings:ICFAccounting` configuration stops startup
with an actionable message, without printing a connection string.
Only SQL repository implementations remain. Runtime registration has no
automatic fallback.

- Both `AddAsync` and `UpdateAsync` retain the existing upsert behavior and save
	changes before returning. Tracked and detached aggregates are supported.
- Reads are detached. Query filtering, sorting, counts, and paging run in SQL;
	callers pass a cancellation token through every database operation.
- Missing identity reads return `null`; removing a missing identity throws
	`KeyNotFoundException`. Inactive records remain visible.
- Pledger lists return all records when no query is supplied. Explicit pledger
	queries default to 20 items. Pledge and payment lists default to 20 items
	even when no query is supplied.
- Name sorting uses the configured SQL collation. Identity tie-breakers use
	native SQL Server GUID ordering: ascending for pledgers and descending for
	pledges and payments. This differs from .NET GUID ordering.
- Foreign keys reject invalid references and referenced deletes. Data translates
	recognized foreign-key failures into `RelationshipConflictException`; API writes
	return sanitized `409 Conflict` ProblemDetails. CHECK violations and unrelated
	database failures retain the generic `500` handling. No optimistic-concurrency
	policy or concurrent-upsert guarantee is introduced.

Run the repository contracts with Docker Desktop running:

```zsh
dotnet test tests/ICFAccounting.IntegrationTests/ICFAccounting.IntegrationTests.csproj --filter FullyQualifiedName~ICFAccounting.IntegrationTests.Repositories
```

Each repository test gets an isolated migrated database in a disposable SQL
Server Testcontainers instance. The tests do not access the Compose database.

All endpoint contract tests now exercise the real SQL repositories. Pledge and
payment tests seed valid parent records before inserting dependent aggregates.
Only deliberate rejecting-service and failing-repository doubles remain for
testing sanitized error responses. SQL-backed registration tests also verify
records remain available after restarting the API host.

```zsh
dotnet test tests/ICFAccounting.IntegrationTests/ICFAccounting.IntegrationTests.csproj --filter "FullyQualifiedName~ServiceRegistrationTests|FullyQualifiedName~SqlServerApiRegistrationTests"
```

### Test Requirements

Domain and Application unit tests do not reference Data or require Docker:

```zsh
dotnet test tests/ICFAccounting.UnitTests/ICFAccounting.UnitTests.csproj
```

Infrastructure and API integration tests require a running Docker Desktop:

```zsh
dotnet test tests/ICFAccounting.IntegrationTests/ICFAccounting.IntegrationTests.csproj
```

The SQL integration collection shares one temporary SQL Server container and
runs its test classes serially to limit Docker resource usage. Endpoint and
repository tests create and drop a uniquely named migrated database per test.
The model tests use a separate database in the same disposable container.
No test reads the developer Compose database or requires its credentials.
Tests fail when Docker is unavailable; they do not silently skip SQL checks or
substitute EF InMemory or SQLite.

## Migrations

The repository pins `dotnet-ef` to the same version as EF Core. Restore it from
the repository root with the .NET 10 SDK installed:

```zsh
dotnet tool restore
```

The design-time factory lives in the Data project, so use Data as both the
project and startup project. It reads `ConnectionStrings__ICFAccounting` from
the process environment. It does not read Compose's environment, a local
`.env` file, application settings, or .NET user-secrets automatically.
Generating migrations or checking model changes does not require credentials
or a running database.

### Create Or Update The Local Database

Start the Compose service first. Prepare a connection string targeting the
local instance and the `ICFAccounting` database, using the existing SQL Server
password. For example, the format is:

```text
Server=localhost,1433;Database=ICFAccounting;User Id=sa;Password=<your local password>;Encrypt=True;TrustServerCertificate=True
```

Use the configured port if `MSSQL_PORT` is not `1433`. Quote password values
containing connection-string delimiters according to SQL Server connection
string rules. `TrustServerCertificate=True` is for the local self-signed
certificate only, not production.

Enter the complete connection string without placing it in shell history:

```zsh
read -rs 'ConnectionStrings__ICFAccounting?ICFAccounting connection string: '
export ConnectionStrings__ICFAccounting
dotnet ef database update --project src/ICFAccounting.Data --startup-project src/ICFAccounting.Data --context ICFAccountingDbContext
```

This command creates `ICFAccounting` if it does not exist, applies the
`InitialCreate` migration, and records it in `dbo.__EFMigrationsHistory`.
The login must have permission to create the database and modify its schema;
`sa` is used here for local development only. No sample data is inserted.
Repeated updates apply only pending migrations. No application-startup
migration or `EnsureCreated` call is used.

Do not commit, print, or log the connection string. Remove it from the shell
when finished:

```zsh
unset ConnectionStrings__ICFAccounting
```

### Review And Evolve The Schema

Check that the current model matches the migration snapshot without connecting
to SQL Server:

```zsh
dotnet ef migrations has-pending-model-changes --project src/ICFAccounting.Data --startup-project src/ICFAccounting.Data --context ICFAccountingDbContext
```

After changing the model, generate a new migration with a descriptive name,
review its generated operations and model snapshot, and run the explicit
database-update command above:

```zsh
dotnet ef migrations add DescriptiveChangeName --project src/ICFAccounting.Data --startup-project src/ICFAccounting.Data --context ICFAccountingDbContext --output-dir Migrations
```

Keep the migration, its designer metadata, and the model snapshot together in
version control. Do not edit or remove migrations already applied to shared
databases. Rolling back the initial migration drops all four tables and their
data; rollback testing uses disposable databases only.

### Model Tests

With Docker Desktop running, execute the focused model tests:

```zsh
dotnet test tests/ICFAccounting.IntegrationTests/ICFAccounting.IntegrationTests.csproj --filter FullyQualifiedName~ICFAccountingDbContextTests
```

Testcontainers starts a separate temporary SQL Server instance with its own
generated credentials and database. These tests do not connect to or alter the
Compose service or its data. They apply the versioned migrations, check schema
and snapshot consistency, and verify that repeated updates are safe. Rollback
and reapplication run in an additional disposable database. The model tests
also cover aggregate round-trips, monetary boundaries, and foreign-key behavior.

## Run The API

Start SQL Server and apply migrations first. Runtime configuration uses the
standard ASP.NET Core providers, including environment variables and .NET
user-secrets in Development. Do not put credentials in committed application
settings, launch settings, or request files.

### Environment Variable

Use the same connection-string format described under migrations. Enter the
complete value through the hidden prompt, then start the API from that shell:

```zsh
read -rs 'ConnectionStrings__ICFAccounting?ICFAccounting connection string: '
export ConnectionStrings__ICFAccounting
dotnet run --project src/ICFAccounting.Api --launch-profile https
```

The HTTPS profile uses `https://localhost:7206` and requires a trusted .NET
development certificate. After stopping the API, clear the shell value with
`unset ConnectionStrings__ICFAccounting`.

### Local User-Secrets

The API project has a user-secrets ID configured. To keep the development
connection string outside the repository between runs, first enter and export
it using the hidden prompt above, then store it locally:

```zsh
dotnet user-secrets set "ConnectionStrings:ICFAccounting" "$ConnectionStrings__ICFAccounting" --project src/ICFAccounting.Api
unset ConnectionStrings__ICFAccounting
dotnet run --project src/ICFAccounting.Api --launch-profile https
```

The launch profile selects Development, where user-secrets are loaded.
Environment variables take precedence if both are configured. User-secrets
are stored outside the repository but are not encrypted; use them only for
local development, not as a production secret store. Remove the saved value
when it is no longer needed:

```zsh
dotnet user-secrets remove "ConnectionStrings:ICFAccounting" --project src/ICFAccounting.Api
```

The standalone Data design-time factory still reads only the environment for
migration commands; saving API user-secrets does not configure that factory.
Neither API startup nor service registration creates or migrates databases.

## Inspect The Database

Use a SQL Server client with these settings:

| Setting | Local value |
| --- | --- |
| Server | `localhost,1433`, or the configured host port |
| Authentication | SQL Server authentication |
| Login | `sa` for local development only |
| Password | The password used to initialize the data volume |
| Database | `ICFAccounting` |
| Encryption | Enabled |
| Trust server certificate | Enabled only for the local self-signed certificate |

Alternatively, run the image's SQL command-line tool without copying the
password into command arguments. Keep `MSSQL_SA_PASSWORD` available in your
local shell so Compose can resolve its configuration:

```zsh
docker compose -f compose.json exec sqlserver /bin/sh -c 'SQLCMDPASSWORD="$MSSQL_SA_PASSWORD" /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -b -d ICFAccounting -Q "SELECT DB_NAME() AS DatabaseName; SELECT MigrationId, ProductVersion FROM dbo.__EFMigrationsHistory;"'
```

This verifies the selected database and applied migration history. Single
quotes ensure the password is expanded inside the container, not by your
local shell. Do not run `docker inspect`, `docker compose config` without
`--quiet`, `dotnet user-secrets list`, or print environment variables when
sharing diagnostic output; these can expose credentials.

## Troubleshooting

| Symptom | Check or action |
| --- | --- |
| Docker daemon cannot be reached | Start Docker Desktop and wait for its engine to become ready; retry `docker info`. |
| Compose reports a missing password | Enter and export `MSSQL_SA_PASSWORD` in the same shell used for Compose commands. |
| Port `1433` is already allocated | Export `MSSQL_PORT=1434` before starting Compose; use `localhost,1434` in the application and migration connection strings. |
| Container stays unhealthy | Check `docker compose -f compose.json ps` and `docker compose -f compose.json logs sqlserver`; verify password complexity and available Docker resources. |
| Login fails after changing the environment password | An existing volume retains its original SQL login password. Use that password or change it through SQL Server; changing the environment alone does not reset it. |
| API stops with a missing connection-string message | Export `ConnectionStrings__ICFAccounting`, or set API user-secrets and use a Development launch profile. The SQL container password variable alone does not configure .NET. |
| EF reports no connection string | The Data design-time factory reads only `ConnectionStrings__ICFAccounting`; API user-secrets and Compose configuration are not read by it. |
| Database cannot be opened, or tables are missing | Apply the explicit migration command against the correct server, port, and database with a login authorized to create the database and schema. |
| HTTPS certificate is untrusted | Run `dotnet dev-certs https --trust` locally and approve the OS prompt. Do not disable certificate validation globally. |
| API port is occupied | Stop the other local API instance or pass a different URL to `dotnet run`, for example `--urls https://localhost:7207`. |
| Integration tests cannot start SQL Server | Ensure Docker is running and can pull the pinned image. These tests fail rather than falling back to an in-memory provider. |
| Tests take several minutes or log intentional failures | SQL tests run serially and create isolated databases. Error-response tests deliberately throw failures; use the final test summary to determine success. |

### Destructive Local Reset

Back up any data you need before resetting. The following command permanently
deletes this Compose project's SQL Server volume, including `ICFAccounting`:

```zsh
docker compose -f compose.json down --volumes
```

Only run it when you intentionally want an empty local instance. Afterwards,
start Compose again and rerun the explicit migration command before using the
API. This is not a password-recovery procedure for data you need to retain.
